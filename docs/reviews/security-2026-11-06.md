## New findings (worst first)

### [medium] N1 — An in-project symlinked managed root still lets a hostile manifest delete files outside the managed subtree (F2 residual)

Where: `src/library-install.js:168-176` (accepts `actualRoot === realProject`), `:195-198`
(lexical owner check), `:214-218` (real-target owner check).

Why it matters: for project scope, the manifest lives in the cloned project and is
attacker-controlled. If the project makes `.agents/skills` (or `.opencode/agents`,
`.junamis/library`) a symlink to the project root, validation accepts that managed root
because its real path equals the real project directory. If the symlink targets `.git` (or
another in-project directory), validation still accepts it because the root only has to be
inside the project. Any manifest entry under the symlink then passes the real-target check
even though it resolves outside the intended skills/agents/docs subtree.
`applyLibraryInstall` will delete such a stale entry when its recorded hash matches (or when
`--force` is used), including project files such as `package.json`, source files, or
`.git/config`.

Evidence (throwaway script, no repository edits): with `.agents/skills -> <project>` and a
manifest entry for `<project>/.agents/skills/package.json`, `applyLibraryInstall({ files: [] })`
deleted `package.json`; with `.agents/skills -> <project>/.git`, it deleted `.git/config`.
The ordinary outside-project cases (symlinked `.junamis`, managed root outside the project,
intermediate symlink, final symlink, `..`, other target's root) were all rejected.

Suggested fix: resolve the expected real root as
`join(realProject, relative(projectDir, root))` and require the actual root to equal it; this
rejects a managed root that is itself a symlink (to the project root, `.git`, or elsewhere)
while still allowing the project directory itself to be reached through a symlink. For
global scope, apply the same expected-real-path rule under `homedir()`.

### [low] N2 — The config gate misses the string form of a bash allow (F14 residual)

Where: `scripts/check-opencode-config.mjs:26-28`, `test/config.test.js:12`.

Why it matters: OpenCode accepts `"bash": "allow"` as a valid permission value. The gate
only reads `perm.bash["*"]`, so a string `"allow"` yields `undefined` and passes. A future
config regression that reintroduces unrestricted bash would therefore pass CI and the test
suite. The same checker also does not look for other broad allow rules (for example a
last-matching `"**": "allow"`).

Evidence: a temp copy of `opencode.json` with `permission.bash = "allow"` made
`node scripts/check-opencode-config.mjs` exit 0; the same copy with an `http://` key or a
`*.vercel.app` key exited 1.

Suggested fix: require `perm.bash` to be a non-array object and reject both
`perm.bash["*"] === "allow"` and a string `perm.bash === "allow"`; add a negative fixture
test for each invariant instead of only asserting the current file passes.

### [low] N3 — `runCommand` can wait indefinitely for a detached descendant that holds stdout/stderr

Where: `src/external.js:207-260` (resolve only on `close`; `SIGKILL` is the last timer and
there is no final fallback), with the same pattern in `src/pinned-source.js:58-124`.

Why it matters: `detached: true` puts the direct child in a new process group, but a
descendant that creates its own session/process group and inherits the pipes is not killed by
the group signal and keeps `close` pending. The installer then hangs even though the timeout
fired, and the checkout is not cleaned up. This is the trade-off of settling only on `close`.

Evidence: a child that spawned a detached 3 s descendant and then exited, run with an 800 ms
`runCommand` timeout, returned `exit 124 elapsed_ms 3074`. A child that ignored `SIGTERM`
with a 500 ms timeout returned `exit 124 elapsed_ms 5521`, which also shows the intended
SIGKILL escalation.

Suggested fix: after the `SIGKILL` timer fires, use a short final grace timer that resolves
(or rejects) even if `close` never arrives, then clean the checkout.

### [low] N4 — A directory at a planned or stale path crashes `install-library` with `EISDIR`

Where: `src/library-install.js:248-252` (planned file path) and `:281-292` (stale path).

Why it matters: `validateLibraryManifest` rejects a symlink final component (`:200-210`) but
not a directory, FIFO, or other non-regular file. `applyLibraryInstall` calls
`sha256(await readFile(path))` unconditionally for paths that exist. A project-controlled
directory at a planned `SKILL.md` path, or at a stale manifest entry, makes the install throw
`EISDIR` instead of reporting a conflict. This is a denial-of-service/robustness bug, not a
deletion bypass.

Evidence: a throwaway `applyLibraryInstall` call with a directory at
`<home>/.agents/skills/route/SKILL.md` threw `EISDIR`.

Suggested fix: `lstat` each path and treat non-regular files as conflicts (or reject the
manifest) before reading.

## Additional observations (informational)

- Global scope does not constrain managed roots to `homedir()`: `src/library-install.js:166-177`
  applies the symlink-escape check only for project scope. A throwaway test with
  `~/.agents/skills` symlinked outside home passed validation and deleted an outside file.
  This requires local write access to the user's home, not a hostile project, so it is not
  counted as a new finding.
- The 64 KiB cap in `src/pinned-source.js:55,103-114` also applies to the local
  `git ls-tree -r` output at `:182`. A legitimate skill tree with a very large file listing
  can therefore fail the install as an "overflow"; the cap is right for remote output but is
  applied to local repository metadata too.
- `stripControlSequences` (`src/external.js:79-93`) does not strip 8-bit C1 controls such as
  U+009B; practical risk is terminal-dependent.
- Several modified/untracked files lack a trailing newline: `src/library-install.js`,
  `scripts/check-opencode-config.mjs`, `scripts/check-pack.mjs`,
  `scripts/check-skills-lock.mjs`, `scripts/release-check.mjs`, `scripts/check-yaml.js`, and
  several `test/*.test.js` files. `git diff --check` is clean; this is only style.
- `atomicWriteFile` (`src/library-install.js:29-34`, `src/guide.js:10-14`) leaves the temporary
  file behind if `rename` fails; it does not clean up in a `finally`.
